# Reply tokens

A reply token is a capability: holding it is the right to answer its one wait. Send it only to the intended replier, such as in an approval link or request metadata. Protect token-bearing discovery output and avoid putting tokens in logs, traces, analytics or broadly accessible inspection output. A leaked token can be used by whoever holds it.

Tokens are opaque base64url strings carrying a version, the instance ID, the engine-issued wait ID and an optional subject digest. The engine does not sign them. Hosts need no token configuration to start, and the fluent builder's in-process `ExecuteAsync` works without host registration. Current tokens use version 3; earlier formats, including signed tokens, are rejected as unknown.

Request activities receive their token through `context.Reply.Token`. Discovery lists only plain event waits; request recipients use the token sent with the request. `ReplyAsync` and the acceptance-only `IWorkflowIngressClient.AcceptReplyAsync` reject malformed or unsupported tokens as unknown (`InvalidRequest`). A well-formed token must address an issued wait in its instance, with the correct subject, event type and matching payload. Closed waits retain their specific rejection reasons. A token cannot answer a later occurrence of a wait with the same name.

For an incoming CloudEvents event request, send the token in `X-IxIFlow-Reply-Token`. Its instance must match the route instance. The endpoint checks its format and route instance before ownership or status reads, then uses the engine's acceptance-only reply path. Authentication, instance authorization and any configured Standard Webhooks body signature still apply. A token targets its wait regardless of the route's event key. An event without this header remains an ordinary keyed notification. Raw target wait IDs are refused by the ingress client.

Operator wait listings contain diagnostic `waitRef` values and no wait IDs or tokens. Token discovery requires the reply policy. Its `nextAfter` cursor plainly encodes a wait reference, contains no wait ID and grants no reply permission; pass it unchanged as `after`. All stores page by that reference using the same ordering and an index on open waits. Trace and snapshot access requires the inspect policy, including authorization against the instance summary, and grants no token discovery permission. Engine traces, snapshots, pending-activity lists and logs carry wait references, never raw wait IDs or reply tokens.
